# Repository workflow contract

This repository inherits the user's global Codex instructions. Keep this file limited to repository
facts and rules that are not already covered there.

## Before work

- Read this file and any closer instruction file.
- Inspect repository status and preserve unrelated or concurrent edits.
- Discover the real build, test, lint, type, format, run, and migration commands before editing.
- Record architecture entry points, persistent data rules, deployment boundaries, and critical
  invariants from the repository itself.

## Routing

- MochiCode Auto remains the only top-level workflow and selects the route automatically from the user's real goal.
- Keep trivial work direct. Use the current selected authority for substantive visual, architectural, tightly coupled, or debugging work, preserving its selected effort. Sol High is the installed default.
- When the running selected parent is `gpt-6-astra`, keep the same work direct in Astra with its selected effort. Catalog omission does not disprove current session identity; catalog support gates new profile installation. Do not add a Manager layer merely because Astra is available. Keep Sol as the installed fallback until matched promotion.
- Direct selected authority is a stock-quality passthrough. Preserve the user's original goal and repository instructions; add no ceremony, optional skill, worker, ledger, or critic without its concrete trigger.
- Keep small or sequential work with the current selected authority. Use a real Luna Medium child only for a sizable independent implementation leaf with a concrete expected saving from leaf size, slow verification, external build latency, isolation, or batch volume; independence alone is insufficient. Escalate to Luna Max after failed acceptance or proven difficulty.
- Fan out only frozen, disjoint leaves under the current selected authority parent. Start with two and use at most three live children per wave until larger waves earn promotion.
- Use Manager Mode beta only for an explicit Manager Mode implementation request; generic implementation or research, review, or planning mentions do not activate it. The current authority parent manages one direct non-spawning Sol High child across phases; bounded state and independent parent verification rotate, park, resume, and permit one replan. Keep automatic classification shadow-only until matched promotion.
- The deterministic controller is experimental and manual until its published promotion gates pass.

## Engineering rules

- Sol High is the default substantive parent and owns product, architecture, visual/UI/UX, tightly coupled implementation, integration, debugging, live verification, and final judgment. A running selected Astra parent takes the same authority and retains its selected effort. Use only efforts advertised by the active host; Ultra is exceptional when supported. Use Max only for consequential whole-product or architecture work.
  Luna Medium handles sizable independent leaves with complete specifications and hard checks. Luna Max is an escalation. Terra is optional only inside an explicitly selected experimental controller run. Record each actual parent and child model and effort; never label parent work as a child model.
  Name each newly created parent task `[ROLE | MODEL | EFFORT] concise objective`. If a child UI label cannot be customized, begin its packet and handoff with those three fields instead. Do not rename existing user tasks or misstate the chosen model or effort.
- Preserve the packet schemas for plan identity, goals, waves, priorities, vertical slices,
  dependencies, acceptance criteria, verification hints, contract commands, protected paths, allowed
  paths, and evidence requirements.
- Exactly one writer owns each file, module, configuration area, migration, or shared state.
- Maximum policy depth is one, current selected authority to child. Children must not spawn descendants. Ordinary native restrictions are behavioral instructions unless host tool denial is verified.
- The Manager Mode implementer is a direct child configured to disable spawning; verify the active host honors that configuration before claiming enforcement. If child creation fails before writing, continue in the direct authority parent.
- Eight active child threads is a host ceiling, not a target. Start with two and use no more than three live workers per wave until a larger wave is benchmark-promoted.
- When observable risk warrants review, use one fresh evidence-bound read-only Sol High verifier, one adjudication by the current selected authority, at most one integrated repair, then rerun all checks and stop. Use three judges only for an explicit benchmark or a consequential multi-domain decision; preserve visual preference for human comparison.
- For consequential interactive behavior, test applicable running, paused, re-entrant, edit-during-run, keyboard-focus, narrow-layout, and actual reduced-motion states.
- Use worktrees or non-overlapping paths for independent writers. Validate every changed instruction,
  TOML, JSON, and skill file with the repository's real checks.
- A future human test is a readiness state, not an automatic blocker. Prepare the testable slice,
  question, and feedback capture, then continue independent reversible work. Report blocked only
  when a real human-only, external, or irreversible gate remains and no useful reversible work exists.
- Internal failures are work, not blockers. Failed controllers or children, missing handoffs/state,
  tool errors, red tests, unresolved architecture, or worktree confusion require a changed method,
  stronger or fresh routing, prerequisite repair, or packet parking while independent work continues.
- Report milestones only. Do not emit repeated waiting updates or empty completed turns. Record each
  child’s role, model and effort, owned paths, tests, result, and stop reason in the handoff artifact.
