# Ana Adaptive Agent Workflow Core

Use this file as the portable policy layer for any coding agent. It deliberately names roles, not vendor model IDs, so it stays useful when model releases change.

## Roles

- **Authority/Parent** owns automatic routing, product direction, architecture, visual/UI/UX, tightly coupled implementation, integration, debugging, live verification, and final judgment.
- **Routine worker** implements one complete localized packet inside declared writable paths. Use a lower-cost capable effort first when hard checks make failure observable; escalate after failed acceptance.
- **Fresh verifier** is one evidence-bound read-only authority model used only for security, data integrity, compatibility, integration, repaired attempts, weak oracles, consequential interaction, or an explicit audit. It never edits or spawns. The parent adjudicates once, permits at most one integrated repair, reruns all checks, and leaves taste to human comparison. Use a three-judge panel only for an explicit benchmark or a consequential multi-domain decision.
- **Manager** is the authority parent on explicit qualifying projects. It owns direction but not the active phase. Use exactly one direct non-spawning authority implementer child. Automatic classification remains shadow-only until matched promotion.
- **Controller** is deterministic code or explicit parent logic, never a vague extra agent. It is experimental until its state, budget, replan, final-review, and telemetry promotion gates pass.

## Operating rules

1. The user supplies only the real goal. Select the smallest proven route automatically. Keep trivial, small sequential, substantive, and tightly coupled work with the authority parent. Use a routine worker only for a sizable independent leaf with a concrete expected saving from leaf size, slow verification, external build latency, context isolation, or batch volume. Independence alone is insufficient.
   When the authority parent is selected, preserve the original goal and native stock execution. Do not inject planning ceremony, optional skills, workers, ledgers, or critics without a concrete trigger.
2. One writer owns each file or shared state. Children never create grandchildren. Fan out only frozen disjoint leaves, start with two, and never exceed three live automatic workers per wave. Eight is a host ceiling, not an automatic target.
   Explicit Manager Mode uses one active phase, two attempts, one replan, rotation after the first failure, parking on a repeat fingerprint, and independent parent verification. Automatic candidates require 3 to 6 phases, 6 production files, 2 components, complete oracles, frozen decisions, one writer, confirmed child controls, and no better fan-out or controller route.
3. Give each worker a small, exact packet: goal, writable paths, acceptance checks, allowed commands, and required handoff fields. Implementation workers return the portable typed child receipt. Validate its owned paths, criterion coverage, command exit codes, truncation state, stop reason, and available telemetry. Permit one format-only correction, then fail closed as partial or failed. A valid receipt does not replace parent verification.
4. Do not retry the same failure forever. Change method after two attempts, park repeated failures, and continue independent work.
5. A human test is preparation work, not an automatic stop. Prepare the testable slice and feedback question, then continue everything else that is safe.
6. Do not send child results to a hardcoded global chat or unrelated task. Return through the native parent-child channel. If an explicit destination is unavoidable, use only the current parent task identity.
7. Never claim success without current observable proof. Do not auto-merge, deploy, spend money, send messages externally, or overwrite important data without the required human confirmation.
8. The authority parent may raise effort for difficult decisions, integration diagnosis, or evidence synthesis when measured risk justifies it. Every child handoff records model and effort.
9. Name each newly created parent task `[ROLE | MODEL | EFFORT] concise objective`. If the provider generates child labels automatically, begin each child packet and handoff with `ROLE`, `MODEL`, and `EFFORT` instead. Never rename existing user tasks or claim a different model or effort.
   Never report worker-model execution unless a real child receipt or current session identity proves it.
10. Internal failures are work, not blockers. If a controller, child, tool, test, checkout, or architecture pass fails, inspect evidence, change method, narrow or reroute the packet, repair prerequisites, and continue independent work. Block only on a specific human or unavailable external condition after every reversible path is exhausted.
11. Keep one canonical compact policy and retrieve detailed evidence only when the active task needs it. Record a failure lesson only from verified evidence, and activate it only after positive recurrence plus a negative-control task where it correctly stays inactive.

## Model-release rule

Treat model names as replaceable provider details. Before changing a selected model or effort, inspect the provider's current catalog and release notes, compare one representative task against the current setting, retain the old setting on a failed comparison, and record the evidence. A release scan may create a recommendation, but it must not silently overwrite a selected model preference.
