# MochiCode Auto brief

## Objective

Make every substantive Codex project prompt automatically enter one quality-first workflow while keeping ordinary one-step questions fast.

## Required result

- The user supplies only the real goal. MochiCode automatically selects the route, model, effort, relevant skills, children, checkpoints, judges, and stop conditions.
- Sol High is the default substantive parent and owns product, architecture, visual/UI/UX, tightly coupled implementation, integration, debugging, live verification, and final judgment. Sol Max is consequential-only.
- Luna Medium owns only sizable independent implementation leaves when a real child receipt proves the route and a concrete saving from leaf size, slow verification, external build latency, context isolation, or batch volume can repay delegation overhead. Independence alone is insufficient. Small sequential work remains direct Sol. Luna Max is escalation after failed acceptance or proven difficulty.
- Terra is absent from the default route and optional only inside an explicitly selected experimental controller run.
- Manager Mode beta activates on an explicit implementation request. Sol owns the checklist and one replan while one direct non-spawning Sol High child implements phases sequentially. The ledger requires independent child and parent receipts, rotates after a first failure, and parks repeats or exhausted attempts. Automatic classification stays shadow-only until matched promotion.
- Deterministic Python owns queues, dependencies, reservations, retries, budgets, fingerprints, pinned identities, persisted-state reconciliation, stop/resume, process containment, evidence, and merge eligibility only on that experimental route.
- A warranted quality gate uses one fresh evidence-bound read-only Sol High verifier, one Sol adjudication, one repair at most, then reruns all checks and stops. Three judges are reserved for an explicit benchmark or consequential multi-domain decision.
- Wave one must create a runnable vertical slice.
- One failed Luna attempt rotates the queue to independent work.
- A second failed attempt, or the first repeated fingerprint, parks the packet.
- No accepted work merges into the user’s current branch automatically.
- A final Sol `MERGE` recommendation stops at a human merge gate; the controller never merges the source branch.
- The supported release is Windows-only. The POSIX/Linux supervisor is experimental and unreachable from release entry points.
- Protected tests, harnesses, measurement inputs, and Python startup-hook paths are covered by protected hashes, workspace fingerprints, and write-path checks.
- Codex saved ChatGPT subscription authentication is required. API keys and provider tokens are filtered from child environments, so missing subscription access blocks with no API-key or paid-billing fallback.
- The documented cloud target is a private user-owned Google Drive folder for redacted bundle/lesson sync. OneDrive is not used.
- Raw logs, prompts/goals, outcomes, diffs, process/PID data, unredacted candidates, secrets, and credentials are excluded from the synced bundle.
- The public before/after benchmark is not yet scored. Docker grading and large image or dependency downloads require explicit approval before they run.

## Non-goals

- Modifying or depending on the historical MochiCode harness repository.
- Copying the archive’s endless backlog refill, stale model prices, disputed lesson scoring, or user-programmable loop language.
- Adding an MCP server.
- Replacing host approvals, hiding spend, or weakening project safety rules.
- Synchronizing live run state concurrently between devices.
- Using OneDrive or another live-sync folder as a release cloud target.

## Acceptance boundary

Local acceptance requires a fresh natural-prompt discovery, the zero-cost stub state-machine demonstration, a contained subscription-backed coding task with reviewed work on a controller-owned integration branch, reversible handling of conflicting automatic routing, and a second capability canary. Google Drive packaging and second-device installation are separate release checks. The public before/after benchmark remains protocol-only and unscored until its approval-gated generation and Docker grading are actually run.
